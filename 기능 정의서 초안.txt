## 기능 정의서


### 사용 스펙
  ㄴ 언어: Java 21
  ㄴ 프레임워크: Spring Boot 3.5.16
  ㄴ 빌드: Maven
  ㄴ DB: H2 2.5.252 서버 모드
  ㄴ DB 접근: MyBatis
  ㄴ 화면: Thymeleaf + 부트스트랩
  ㄴ 데이터 모양: Map<>, List<>, VO(Lombok), DTO(record)
  ㄴ JSON: Jackson, ResponseEntity
  ㄴ 인증: Spring Security
  ㄴ 테스트: JUnit 5
  ㄴ 도구: IntelliJ, H2 콘솔, GitHub, 브레이크포인트 디버깅 모드, 크롬 개발자 도구

(참고사항) 롬복 VO와 record는 연습용으로 둘 다 사용

### 회원
- 기본 CRUD: 회원가입, 로그인, 회원정보 수정, 회원탈퇴
- 부가 기능: 내 정보 자세히 보기(마이 페이지)

### 게시판
- 기본 CRUD: 게시글 작성, 게시글 목록 읽기, 게시글 자세히 보기, 게시글 수정, 게시글 삭제
- 부가 기능: 게시글에 파일 업로드
- 추가 기능 후보(현재 범위 밖): 게시글 추천(추천 수). 만들 경우 숫자 칸 하나로 할지, "누가 추천했는지" 별도 테이블로 할지(중복 추천 방지) 결정 필요

## URL 정의서
- 각각 템플릿, 라우트 | 메서드 방식 및 설명

### 메인
- 메인 화면: index.html, "/"

### 회원
- 회원가입: join.html, "/member/join" | GET 회원가입 화면, POST 회원가입 프로세스 (DB 레코드 신규생성)
- 로그인: login.html, "/member/login" | POST 로그인 프로세스
- 로그아웃: 없음, "/member/logout" | GET 로그아웃 (세션 지우기)
- 마이페이지: mypage, "/member/mypage" | GET 마이페이지
- 회원정보 수정: member_edit, "/member/edit" | GET 수정 화면, POST 수정 프로세스 (DB 레코드 수정)
- 회원탈퇴: 없음, "/member/delete" | POST 회원탈퇴 프로세스 (DB 레코드 수정/의미적 삭제처리)


### 게시판
- 게시글 등록: board_post, "/board/post" | GET 게시글 작성 화면, POST 게시글 저장 프로세스 (DB 레코드 신규생성)
- 게시글 목록 읽기: board_list, "/board/list" | GET 게시글 전체 목록
- 게시글 자세히 보기: board_view, "/board/view/<index>" | GET 게시글 자세히 보기
- 게시글 수정: board_edit, "/board/edit/<index>" | GET 게시글 수정 화면, POST 게시글 수정 로직 (DB 레코드 수정)
- 게시글 삭제: board_delete, "/board/delete/<index>" | POST 게시글 숨기기 로직 (DB 레코드 수정/의미적 삭제처리)

## h2 DB 쿼리

### 테이블(member, board)

create table member(
member_idx int AUTO_INCREMENT PRIMARY KEY, -- 회원번호(PK)
user_id varchar(50) not null UNIQUE, -- 사용자 계정
pwd varchar(250) not null, -- 사용자 비밀번호
name varchar(50) not null, -- 사용자 이름
role enum('user','admin') not null default 'user', -- 권한등급
use_yn enum('Y','N') not null default 'Y', -- 활성화 여부(Y시 활성화 판정)
reg_dttm timestamp not null default current_timestamp, -- 가입 시각
upt_dttm timestamp, -- 회원정보 마지막 수정 시각(수정 전엔 NULL)
del_dttm timestamp -- 탈퇴 시각(use_yn을 'N'으로 바꿀 때 기록, 탈퇴 전엔 NULL)
);


create table board(
board_idx int AUTO_INCREMENT PRIMARY KEY, -- 게시글번호(PK)
title varchar(255) not null, -- 게시글 제목
content varchar(3000), -- 게시글 내용
member_idx int not null, -- 글쓴이(회원번호 연동/FK)
del_yn enum('Y','N') not null default 'N', -- 게시글 삭제 여부(Y시 삭제 판정)
reg_dttm timestamp not null default current_timestamp, -- 생성 시 시간 기록(등록자 = 글쓴이 member_idx)
upt_member_idx int, -- 마지막 수정자 회원번호(수정 전엔 NULL)
upt_dttm timestamp, -- 마지막 수정 시각(수정 전엔 NULL)
del_member_idx int, -- 삭제(숨김) 처리한 회원번호(글쓴이 또는 admin, 삭제 전엔 NULL)
del_dttm timestamp, -- 삭제(숨김) 처리 시각(del_yn을 'Y'로 바꿀 때 기록, 삭제 전엔 NULL)
CONSTRAINT member_fk FOREIGN key(member_idx) REFERENCES member(member_idx) -- member테이블 member_idx와 FK
);


create table board_file (
file_idx int auto_Increment not null primary key, -- 파일번호(PK)
board_idx int not null, -- 저장한 게시글 출처(board 연동 FK)
file_original_name varchar(255) not null, -- 파일 원래 이름
file_save_name varchar(100) not null, -- 파일 저장시 이름
file_size bigint not null, -- 파일 크기
del_yn enum('Y', 'N') not null default 'N', -- 삭제 처리 여부
reg_dttm timestamp not null default current_timestamp, -- 저장 날짜
del_dttm timestamp, -- 삭제 처리 날짜
constraint board_file_fk foreign key(board_idx) references board(board_idx) -- board 테이블 board_idx와 FK
);


### FK의 특징. 장단점.

특징:
- FK는  부모 테이블까지 검사하며 검증이 끝나기 전까지 해당 줄에 락을 건다(줄을 처리할 때 다른 곳에서 해당 줄을 수정해버리면 안되기에)
- 락은 트랜젝션이 끝날 시 풀린다.

장점:
- 데이터 변화 시 잘못된 참조를 방지한다(정합성)
- 관계형 데이터베이스의 장점, 테이블만 봐도 관계성을 알아보기 쉽다.

단점:
- 검증할 때 추가 연산이 발생하며, 성능 저하를 일으킨다.
- 테이블을 삭제할 시, 자식 먼저 삭제 > 부모 삭제 순서를 지켜야 하며, 관계형 데이터베이스는 자식이 또 다른 자식의 부모일 수도 있으므로, 관리가 쉽지 않다. CASCADE로 어느정도 커버할 수 있다. > 하지만 예상치 못한 대량 삭제 유발 가능성이 있다. 부모 삭제 시 자식도 같이 삭제


### 결론: 이 프로젝트에선 어떻게 사용할건가
- member_idx 만 사용.

이유: 게시판은 부모인 회원과 관계성을 가지는 것이 자연스럽다고 판단. 또한 FK를 건 케이스와 걸지 않은 케이스를 둘 다 체험해보고자 함.
예상되는 단점: 다른 관계성 후보인 마지막 수정자 회원 번호는 제외했기에, 전체 코드에서의 의도가 불투명해질 수 있다(여긴 왜 이렇게 했데?)
